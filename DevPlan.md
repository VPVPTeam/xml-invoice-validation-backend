# Dev Plan — XML Invoice Validation Backend

Форвард-лукинг роадмап. **Сверяться перед добавлением любой новой фичи** —
чтобы архитектура закладывалась под будущие направления и не переделывалась.

## Подход к разработке (резюме-ориентированный)

Приоритет — фичи, которые **отдельной строкой идут в резюме и обсуждаются на
собеседовании**: тесты, Docker, CI/CD, облако, многопоточность, очереди сообщений.
Это переносимые технические навыки и инструменты, востребованные повсеместно.

Доменные фичи (RuleGroup, common/private правила и т.п.) marketable-навыком не
являются — их нельзя показать в CV или на собесе, поэтому они **отложены** в раздел
«ХЗ когда» и делаются только после основной, резюме-значимой части.

**Рабочий цикл для каждой фичи:**
1. Реализовать фичу.
2. Написать под неё тесты.
3. Смерджить в `dev`.
4. Убедиться, что pipeline зелёный и версия задеплоена.

Пункт 4 становится выполнимым только после того, как будут готовы Docker, CI/CD и
облако — поэтому они идут в начале очереди, а не в общем порядке.

## Статус

- **Аутентификация — сделана.** Пользователи, роли, JWT, вход, `/me`, создание
  пользователей администратором, ограничения доступа.
- **Глобальные (интеграционные) тесты — сделаны.** 53 теста, Testcontainers +
  PostgreSQL в Docker. Покрыты все эндпоинты всех контроллеров: успешные сценарии
  и все обрабатываемые ошибки.
- **Текущий этап — рефакторинг** (ветка `refactor/cleanup`).

# Текущий этап: рефакторинг

## Принципы этапа

- **Тесты — страховочная сеть.** Они не зависят от внутренней структуры классов,
  поэтому рефакторинг их ломать не должен. Если сломались — сначала проверить,
  не утверждает ли тест деталь реализации вместо поведения.
- **Прогон всех тестов после каждого шага**, а не в конце: тогда причина падения
  известна сразу.
- **Отдельный коммит на каждый шаг** — неудачный шаг откатывается один.
- **Размер метода — симптом, а не диагноз.** Резать по числу строк нельзя:
  получится дробление, при котором один сценарий приходится собирать из десятка
  трёхстрочных методов. Настоящий критерий — **смешение уровней абстракции** и
  **несколько причин для изменения**.
- **Абстракции выделять по необходимости, а не ради выделения.** Интерфейс или
  абстрактный класс оправданы, когда есть вторая реализация либо реальная
  потребность развязать зависимость. Интерфейс с единственной реализацией —
  спекулятивное обобщение, оно только добавляет слой. Оправданные абстракции в
  проекте уже есть: `FormatProcessor` и `TechnicalValidator<T>` (за ними стоит
  требование поддержать несколько форматов).
- **Этап считается законченным, когда закрыт список ниже**, а не «когда станет
  красиво». Иначе полировка бесконечна.

## Найденные проблемы

**1. `ValidationService.validateBatch` — 90 строк, пять ответственностей.**
В одном методе: обработка пустого батча, парсинг с перехватом, определение
дубликатов двух видов, накопление нарушений, сбор идентификаторов, запуск
бизнес-валидации, сохранение. Уровни абстракции перемешаны.

**2. `ValidationIssue` создаётся конструктором с восемью позиционными аргументами**,
пять из которых подряд — строки. Перепутать местами компилятор не помешает.
Встречается по коду около восьми раз.

**3. Композиция `invoiceId` продублирована в трёх местах** — `ValidationService`,
`ValidationOutput.invoiceId()`, `InvoiceValidationController.getBatchesByInvoice`.
Доменное понятие без своего дома.

**4. `InvoiceValidationController.validateXmlInputs` делает работу сервиса** —
конвертирует `MultipartFile` в `XmlFileData`, проверяет формат. Хуже:
`catch (Exception ex)` вокруг вызова сервиса превращает **любую** внутреннюю
ошибку в «XML file is invalid» с кодом 400, маскируя баги под проблему клиента.

**5. `ValidationPersistenceService` — три несвязанные ответственности:**
сохранение результата валидации, CRUD вендоров, CRUD правил. Плюс три
перегруженных `save()` для разных типов.

**6. `ValidationOutput` — публичные сеттеры и бизнес-логика одновременно.**
Посчитанные счётчики может перезаписать кто угодно; инвариант
`validInvoices + invoicesWithIssues = totalInvoices` ничем не защищён.

**7. `KsefTechnicalValidator.checkRequired` — шесть позиционных параметров**,
вызывается около двадцати раз. Та же проблема с порядком аргументов.
Плюс класс совмещает проверку полей и запуск построения канонической модели.

**8. Мелочи.** Проверить, используется ли `FieldCheck.notEmpty`;
`resolveStatus` проверяет `issues` на `null`, хотя поле инициализировано;
`getSupportedFormats()` в сервисе существует только ради проверки в контроллере.

## Порядок работ

`ValidationService` задевают пять пунктов из восьми, поэтому его разбиение идёт
**не первым**: сначала приводим в порядок содержимое строк, потом переставляем их
по методам. Перемещать чистый код дешевле, чем повторно резать грязный.

**Шаг 1. Идентичность фактуры и безопасное создание нарушений (пункты 2 + 3).**
Это одно решение, а не два: если у `invoiceId` появляется свой тип, встаёт вопрос,
не должен ли `ValidationIssue` хранить его вместо двух отдельных строк — а именно
эти две строки и делают конструктор опасным. Задевает `ValidationIssue`,
`ValidationService`, `BusinessValidator`, `KsefTechnicalValidator`,
`ValidationOutput`, `InvoiceValidationController`.

**Шаг 2. `KsefTechnicalValidator.checkRequired` (пункт 7).**
Та же проблема позиционных аргументов, решается средствами шага 1. Файл изолирован.

**Шаг 3. Инкапсуляция `ValidationOutput` (пункт 6).**
Ограничение, которое надо учесть сразу: `ValidationPersistenceMapper` **собирает**
`ValidationOutput` из сущности через сеттеры. Если сеттеры убрать, нужен другой
способ построения — решение принимается сразу для обоих сценариев: «посчитали при
валидации» и «прочитали из базы». Обязательно до разбиения сервиса, потому что
меняет то, как сервис накапливает результат.

**Шаг 4. Разбиение `ValidationService` (пункт 1).**
К этому моменту содержимое уже чистое — остаётся перестановка по уровням
абстракции. Побочная выгода: разложенная на шаги обработка одного файла
параллелится тривиально, а нынешний цикл — нет. То есть шаг окупится ещё раз,
когда дойдём до многопоточности.

**Шаг 5. Разгрузка контроллера (пункт 4).**
После того как у сервиса появится внятный вход.

**Шаг 6. Разделение `ValidationPersistenceService` (пункт 5).**
Независим от остальных, задевает два контроллера и сервис. В конце, когда всё
вокруг стабильно.

**Шаг 7. Мелочи (пункт 8)** и то, что всплывёт по ходу.

## MVP+ — очередь работ (после рефакторинга)

### 1. Точечные юнит-тесты

Пишем **не на всё оставшееся**, а на стабильное ядро валидации — то, что не будет
переписано ни ближайшими фичами (многопоточность, очереди), ни отложенными
(RuleGroup, per-user правила). Тест на код, который скоро заменят, придётся
выбросить вместе с ним.

- **`OperatorEvaluator`** — главный кандидат. Чистая функция без состояния;
  переживёт и распараллеливание, и RuleGroup (атомарный движок переиспользуется
  как есть). Покрыть: все восемь операторов, `null`-значение, нечисловая строка
  для числового оператора, регистронезависимость, формат `BETWEEN`, перевёрнутый
  диапазон.
- **`KsefTechnicalValidator`** — десятки проверок обязательных полей, из которых
  интеграционными покрыты две. Ничем из планов не затрагивается.
- **`FieldValueExtractor`** — маленький, но ветка с отсутствующим значением
  проверки заслуживает.
- **`ValidationOutput.calculateBatchTotals`** — арифметика счётчиков: сочетания
  дубликатов, технических и бизнес-нарушений. Интеграционными такую комбинаторику
  покрывать неправильно — каждый прогон поднимает контекст, а случаев десятки.
- **`ValidationPersistenceMapper`** — полнота маппинга, **без маппинга правил**
  (его перепишет RuleGroup). Ловит ошибки вида «поле забыли перенести» — ровно тот
  класс дефектов, что уже есть с `message`. Заодно делает безопасным возможный
  переход на MapStruct.
- **`UserService`** — упражнение с Mockito: подменяются репозиторий и кодировщик
  паролей. Проверить конфликт по занятому email и то, что в базу уходит хеш.

**Не покрываем сознательно:** `ValidationService` (будет переписан под
многопоточность, поведение уже держат интеграционные тесты), `BusinessValidator`
(его цикл переписывает RuleGroup), классы сообщений, `CanonicalFieldRegistry`,
записи и DTO.

### 2. Docker

Свой образ приложения. Docker в проекте уже фактически задействован через
Testcontainers, так что шаг короткий.

### 3. CI/CD

Pipeline, который на каждый push собирает проект и прогоняет весь набор тестов.
Тесты для этого уже готовы — pipeline будет не декоративным.

### 4. Cloud

Деплой. После этого шага рабочий цикл начинает выполняться полностью.

### 5. Дальше

- Многопоточность (параллельная обработка батча).
- Kafka / RabbitMQ (асинхронная обработка).
- Документация кода.
- Кастомные аннотации.

- Счётчик нечитаемых файлов (файл с ошибкой разбора не попадает ни в один счётчик).

## Дизайн: RuleGroup (целевая модель)

- Rule = группа условий: `(vendor, name/key, is_active, combinator AND|OR, conditions[])`.
- Condition = `(field_path, operator, expected_value)` — нынешнее атомарное правило.
- Верхний уровень: все активные группы соединяются через AND. Внутри группы —
  её комбинатор. **Один уровень вложенности, без полного булева дерева.**
- Богатые операторы (`IN`, `BETWEEN`) уже покрывают «ИЛИ внутри поля» и диапазоны —
  не плодить условия зря.
- Активация и версионирование — на уровне группы (не per-field).
- **DRY: атомарный движок (`OperatorEvaluator`, `FieldValueExtractor`,
  `CanonicalFieldRegistry`) переиспользуется без изменений**; новое — только тонкий
  слой композиции результатов условий. Именно поэтому эти классы можно спокойно
  покрывать юнит-тестами уже сейчас.
- Репортинг: одно нарушение на упавшую группу (гасим шум предупреждений).
- У каждой RuleGroup будет свой овнер; ключ активной уникальности обрастёт `owner`
  → `(owner, vendor_id, field_path)`.

## Дизайн: Auth (реализовано, справочно)

- Таблица `app_user`, роли одной колонкой, пароли — BCrypt.
- JWT: один access-токен (~1 час), stateless; фильтр подгружает пользователя из
  базы, поэтому деактивированный не проходит даже с живым токеном.
- Первый администратор — через сеятель (`AdminSeeder`) из конфигурации.
- Vendor: создание, изменение, удаление — только ADMIN.
- Отложено: refresh-токен; владение правилами (часть RuleGroup).

## Тестовая инфраструктура (как устроена)

- **Один контейнер PostgreSQL на весь прогон** — запускается в статическом блоке
  `AbstractIntegrationTest`; аннотации `@Testcontainers` / `@Container` НЕ
  используются. Причина: они гасят контейнер после каждого класса, а контекст
  Spring кешируется — второй класс получал бы мёртвое соединение.
- **Схема** подаётся через `withInitScript("schema.sql")` из `src/test/resources`;
  в тестовой копии не должно быть блока `DROP`.
- **Очистка между тестами** (`@BeforeEach`): `TRUNCATE` таблиц валидации, правил и
  вендоров + удаление всех пользователей, кроме администратора (его создаёт сеятель
  один раз при старте контекста, восстановить иначе нечем).
- **`AbstractIntegrationTest`** даёт наследникам: `mockMvc`, `adminToken()`,
  `userToken()`, `tokenFor()`, `authorizedGet()`, очистку базы.
- **`InvoiceFixture`** — запись с данными тестовых фактур (файл, налоговый номер,
  номер фактуры, название вендора) и методом `invoiceId()`.

### Правила написания тестов

- **Тесты не привязаны к внутренней структуре** — только к API и ответам.
- **Достаточность:** основной сценарий + все ошибки, которые код обрабатывает явно.
  Не гнаться за недостижимыми защитными ветками.
- **`401`:** один тест на контроллер, не на каждый эндпоинт. Общее правило
  `anyRequest().authenticated()` одно на приложение, а исключения (`permitAll`)
  добавляют по префиксу пути, то есть фактически по контроллеру.
- **`403`:** тест на каждый метод с `@PreAuthorize` — аннотация стоит на методах
  по отдельности, и пропажу одной поймает только её собственный тест.
- **Утверждения:** проверять итог сценария (статус, нарушения, счётчики), а не всё
  подряд — избыточные проверки делают тесты хрупкими. Тексты сообщений об ошибках
  фиксировать точно; формулировки, которые могут меняться, — через вхождение
  подстроки.
- **Подготовка данных — через репозитории**, а не через API: иначе поломка CRUD
  роняет чужие тесты и путает диагностику.
- **Порядок элементов не утверждать** — использовать `containsInAnyOrder`.
- **DAMP важнее DRY:** выносить в помощники подготовку, но не ожидаемые значения —
  тест должен читаться сверху вниз без переходов по файлу.

## Технические нюансы — окружение и фреймворк (грабли)

- **Spring Boot 4 / Spring MVC 7:** маршруты матчатся БЕЗ трейлинг-слеша.
  `/api/vendors/` ≠ `/api/vendors` → 500 (`NoResourceFoundException`).
- **Jackson XML — это `tools.jackson.*` (Jackson 3.x), НЕ `com.fasterxml.jackson.*`.**
- **`@AutoConfigureMockMvc` в Boot 4 переехал** в модуль `spring-boot-webmvc-test`,
  пакет `org.springframework.boot.webmvc.test.autoconfigure`.
- **Testcontainers не управляется BOM Spring Boot** — версию задавать самим
  (свойство `testcontainers.version`).
- **`ddl-auto: validate`:** Hibernate таблицы НЕ создаёт и НЕ проверяет строго
  nullability.
- **PostgreSQL `TIMESTAMPTZ` в нативном запросе приходит как `java.time.Instant`,
  не `OffsetDateTime`.** Конвертить: `((Instant) row).atOffset(ZoneOffset.UTC)`.
- **Порядок flush у Hibernate:** на коммите сначала INSERT, потом UPDATE, потом
  DELETE. Если констрейнт требует «сначала обновить, потом вставить» — форсить
  `repository.flush()`.
- **Lombok + boolean:** поле называть `active` (не `isActive`).
- **AOP-прокси:** бины с `@Transactional` / `@PreAuthorize` / `@Async` НЕ должны
  быть `final`.
- **Spring Security 6+:** отказ от `@PreAuthorize` бросает `AccessDeniedException`
  во время вызова метода (не в фильтре) → ловится в `ApiExceptionHandler` (403).
  Неаутентифицированный запрос без явного `AuthenticationEntryPoint` даёт 403,
  а не 401 — нужен entry point с 401.
- **Перегрузка + переменное число аргументов** легко даёт неоднозначность: вызов
  с одним аргументом подходит и `f(String...)`, и `f(String, T...)` (второй —
  с пустым списком). Проще давать разные имена.
- **JWT (jjwt 0.13):** сериализатор `jjwt-gson` (независим от Jackson); секрет
  ≥ 32 символов для HS256, брать из переменной окружения.

## Доменные решения и конвенции

- **`invoiceId` = `sellerTaxId + "|" + invoiceNumber`**; при отсутствии налогового
  номера продавца подставляется `UNKNOWN`.
- **`CanonicalFieldRegistry` — единственный источник правды по `field_path`.**
- **Операторы:** разделитель `BETWEEN` = `;`, `IN`/`NOT_IN` = `,`; строковые
  операторы регистронезависимы; `OperatorEvaluator` НИКОГДА не бросает —
  безопасный парсинг через `Optional`.
- **Двухэтапная валидация:** бизнес-этап запускается ТОЛЬКО после успешной
  технической проверки.
- **Ошибка разбора XML не роняет батч** — превращается в нарушение
  `TECH_XML_PARSE_ERROR`, остальные файлы обрабатываются.
- **Severity бизнес-issue = WARNING**, никогда ERROR.
- **Дубликаты:** in-batch (Set) + cross-batch (DAO), оба WARNING; cross-batch не
  прерывает обработку. Дубликаты — **отдельная информационная ось**, в
  `invoicesWithIssues` не попадают.
- **Счётчики `ValidationOutput`:** считаются от уникальных фактур; инвариант
  `validInvoices + invoicesWithIssues = totalInvoices`.
- **`ValidationIssue.message`** — одна чистая фраза, без `\n` и без дублирования
  полей, которые есть отдельно.
- **API-ответы:** коллекции → `ListResponse<T>` с record-DTO; POST/PUT возвращают
  ресурс; DELETE → 204. **Все ошибки — единым форматом `ErrorResponse`.**
- **Уникальность проверяем в коде** + констрейнты БД как страховка.

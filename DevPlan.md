# Dev Plan — XML Invoice Validation Backend

Форвард-лукинг роадмап. **Сверяться перед добавлением любой новой фичи** —
чтобы архитектура закладывалась под будущие направления и не переделывалась.

## Подход к разработке (резюме-ориентированный)

Приоритет — фичи, которые **отдельной строкой идут в резюме и обсуждаются на
собеседовании**: тесты, многопоточность, Docker, CI/CD, облако, очереди сообщений.
Это переносимые технические навыки и инструменты, востребованные повсеместно.

Доменные фичи (RuleGroup, common/private правила и т.п.) marketable-навыком не
являются — их нельзя показать в CV или на собесе, поэтому они **отложены** в раздел
«ХЗ когда» и делаются только после основной, резюме-значимой части.

**Рабочий цикл для каждой резюме-фичи:**
1. Реализовать фичу.
2. Написать под неё тесты.
3. Довести до рабочей, деплоящейся версии (Docker → облако → pipeline).

Цель — после каждой фичи получать не только кодовые знания, но и владение
инструментами разработки.

## Текущий фокус

1. **Глобальные (интеграционные) тесты** — покрывают концепцию приложения целиком
   (сквозные сценарии через API + БД). Пишутся так, чтобы **не зависеть от
   внутренней структуры** методов и классов — тогда они переживут последующий
   рефакторинг и будут страховочной сетью для него.
2. **Рефакторинг** под прикрытием этих тестов:
- SOLID;
- абстрактные классы / интерфейсы;
- ООП.
3. **Юнит-тесты** для остальных частей кода (то, что не покрыто интеграционными).

## MVP+ — резюме-фичи (технические навыки и инструменты)

Делаются постепенно, каждая — по рабочему циклу выше (фича → тесты → деплой):

## ХЗ когда (после резюме-части)

### В первую очередь
- **RuleGroup** (дизайн сохранён ниже, в разделе «Дизайн: RuleGroup»):
  - при добавлении правила гасить предыдущее активное, если конфликт по
    `(vendor_id, field_path)`, и сообщать пользователю (`BusinessRuleSaveResult`);
  - несколько правил на одно поле;
  - в отчёт добавить, по каким правилам шла бизнес-валидация.
- Таблица правил в разрезе юзеров: common / private.

### Доп. фичи
- Больше GET-эндпоинтов.
- Логи (structured logging).
- Мапперы → MapStruct (?) — не тривиально: Lombok-интеграция
  (annotationProcessorPaths + lombok-mapstruct-binding) и нестандартные маппинги
  (два аргумента, двунаправленный addIssue, конструктор-инъекция).
- Refresh-токен для аутентификации.
- Мягкое удаление (soft delete) для Vendor — защита от случайного удаления
  (сейчас `ON DELETE CASCADE` стирает правила безвозвратно).

## Дизайн: RuleGroup (целевая модель, для будущего)

- Rule = группа условий: `(vendor, name/key, is_active, combinator AND|OR, conditions[])`.
- Condition = `(field_path, operator, expected_value)` — нынешнее атомарное правило.
- Верхний уровень: все активные группы соединяются через AND. Внутри группы —
  её комбинатор. **Один уровень вложенности, без полного булева дерева.**
- Богатые операторы (`IN`, `BETWEEN`) уже покрывают «ИЛИ внутри поля» и диапазоны.
- Активация и версионирование — на уровне группы (не per-field).
- DRY: атомарный движок переиспользуется как есть; новое — только тонкий слой
  композиции результатов условий.
- Per-user активация и common/private — опираются на аутентификацию (уже готова).
- У каждой RuleGroup будет свой овнер.
- **Текущая → целевая:** сейчас «одно активное правило на поле
  (vendor_id + field_path UNIQUE)». RuleGroup её меняет: несколько правил на поле,
  активность на уровне группы, ключ активной уникальности обрастёт `owner`
  → `(owner, vendor_id, field_path)`.

## Аутентификация — что сделано (справочно)

- Таблица `app_user`, роли `USER`/`ADMIN` (одной колонкой), BCrypt.
- JWT (один access-токен, ~1 час), stateless, фильтр проверки токена.
- Вход `/api/auth/login`, «кто я» `/api/auth/me`, создание пользователей
  администратором (`@PreAuthorize("hasRole('ADMIN')")`).
- Первый администратор — через сеятель (`AdminSeeder`) из конфигурации.
- Удаление/изменение/создание вендора — только ADMIN.
- Отложено (в «ХЗ когда»): refresh-токен; владение правилами (per-user) — часть RuleGroup.

## Технические нюансы — окружение и фреймворк (грабли, на которые уже наступали)

- **Spring Boot 4 / Spring MVC 7:** маршруты матчатся БЕЗ трейлинг-слеша.
  `/api/vendors/` ≠ `/api/vendors` → 500 (NoResourceFoundException).
- **Jackson XML — это `tools.jackson.*` (Jackson 3.x), НЕ `com.fasterxml.jackson.*`.**
- **`ddl-auto: validate`:** Hibernate таблицы НЕ создаёт (только `schema.sql`) и НЕ
  проверяет строго nullability. `@Column(nullable=false)` держать синхронно с `NOT NULL`.
- **PostgreSQL `TIMESTAMPTZ` в нативном запросе приходит как `java.time.Instant`,
  не `OffsetDateTime`.** Конвертить: `((Instant) row).atOffset(ZoneOffset.UTC)`.
- **Порядок flush у Hibernate:** на коммите сначала INSERT, потом UPDATE, потом
  DELETE. Если констрейнт требует «сначала обновить, потом вставить» — форсить
  `repository.flush()` между операциями.
- **Lombok + boolean:** поле называть `active` (не `isActive`) → геттер `isActive()`.
- **AOP-прокси:** бины с `@Transactional`/`@PreAuthorize`/`@Async` НЕ должны быть
  `final` (CGLIB создаёт прокси подклассом; `final` ломает старт).
- **Spring Security 6:** `@PreAuthorize`-отказ бросает `AccessDeniedException` уже во
  время вызова метода (не в фильтре) → обрабатывается в `ApiExceptionHandler` (403).
  Неаутентифицированный запрос без явного `AuthenticationEntryPoint` даёт 403, а не
  401 — нужен entry point, возвращающий 401.
- **JWT (jjwt 0.13):** сериализатор `jjwt-gson` (независим от Jackson); секрет ≥ 32
  символов для HS256, брать из переменной окружения, не из репозитория.

## Доменные решения и конвенции (наши, чтобы не переоткрывать)

- **`invoiceId` = `sellerTaxId + "|" + invoiceNumber`** — композитный ключ фактуры.
- **`CanonicalFieldRegistry` — единственный источник правды по `field_path`.**
- **Операторы:** разделитель `BETWEEN` = `;`, `IN`/`NOT_IN` = `,`; строковые операторы
  регистронезависимы (`equalsIgnoreCase` / `Locale.ROOT`); `OperatorEvaluator` НИКОГДА
  не бросает (безопасный парсинг через `Optional`).
- **Двухэтапная валидация:** бизнес запускается только если техническая прошла.
- **Severity бизнес-issue = WARNING**, никогда ERROR.
- **Дубликаты:** in-batch (Set) + cross-batch (DAO), оба WARNING; cross-batch без
  `continue`.
- **Счётчики `ValidationOutput`:** от distinct-фактур; инвариант
  `validInvoices + invoicesWithIssues = totalInvoices`.
- **`ValidationIssue.message`** — одна чистая фраза, без `\n`, без дублирования полей.
- **Известный пробел:** `ValidationIssueEntity` НЕ хранит `message` → при чтении из БД
  message = null.
- **API-ответы:** коллекции → `ListResponse<T>` с record-DTO; POST/PUT возвращают
  ресурс; DELETE → 204.
- **Уникальность проверяем в коде** + констрейнты БД как страховка (defense in depth).
- **`@NotBlank` строже, чем `NOT NULL`** — три слоя валидации.
- **Пароли — только хеш (BCrypt)**; доменная модель `User` пароль/хеш НЕ содержит;
  ввод пароля — отдельный request-DTO, наружу не сериализуется.
- **`handleUnexpected` обязан логировать** исключение.

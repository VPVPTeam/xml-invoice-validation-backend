# Dev Plan — XML Invoice Validation Backend

Форвард-лукинг роадмап. **Сверяться перед добавлением любой новой фичи** —
чтобы архитектура сразу закладывалась под будущие направления и не переделывалась.

## Roadmap

### MVP+ — Аутентификация (делаем ПЕРВОЙ)
- Пользователи, роли, управление доступом.
- Основание для: vendor delete только админом, per-user правила,
  пользовательская активация RuleGroup.

### MVP++
- **RuleGroup** (см. «Дизайн: RuleGroup»):
    - несколько условий на одно поле, работающих в связке;
    - активация/деактивация на уровне группы; при конфликте по
      `(vendor_id, field_path)` предыдущее активное гасится, юзеру сообщается
      (`BusinessRuleSaveResult`);
    - репортинг: один issue на упавшую группу (гасим шум ворнингов);
    - в отчёт добавить, по каким правилам/группам шла бизнес-валидация.
- Vendor удаляется только админом (нужны роли → после auth).
- Таблица правил в разрезе юзеров: common / private.
- Рефакторинг: SOLID, абстрактные классы/интерфейсы, ООП.

### MVP+++
- Многопоточность (параллельная обработка батча).
- Kafka / RabbitMQ (асинхронная обработка).
- Тесты.
- Docker.
- CI/CD.
- Cloud.
- Рефакторинг.
- Документация кода.
- Кастомные аннотации.

### Backlog (ХЗ когда)
- Больше GET-эндпоинтов.
- Логи (structured logging).
- Мапперы → MapStruct — в блоке рефакторинга. Не тривиально: Lombok-интеграция
  (annotationProcessorPaths + lombok-mapstruct-binding) и нестандартные маппинги
  (два аргумента, двунаправленный addIssue, конструктор-инъекция). Планировать
  отдельную сессию, не «между делом».

## Дизайн: RuleGroup (целевая модель)

- Rule = группа условий: `(vendor, name/key, is_active, combinator AND|OR, conditions[])`.
- Condition = `(field_path, operator, expected_value)` — нынешнее атомарное правило.
- Верхний уровень: все активные группы соединяются через AND. Внутри группы —
  её комбинатор. **Один уровень вложенности, без полного булева дерева.**
- Богатые операторы (`IN`, `BETWEEN`) уже покрывают «ИЛИ внутри поля» и диапазоны —
  не плодить условия зря.
- Активация и версионирование — на уровне группы (не per-field).
- DRY: атомарный движок переиспользуется как есть; новое — только тонкий слой
  композиции результатов условий.
- Per-user активация и common/private — только после auth.
- У каждой RuleGroup будет свой овнер.
- **Текущая → целевая:** в CLAUDE.md сейчас «одно активное правило на поле
  (vendor_id + field_path UNIQUE)» — это текущая модель. RuleGroup её меняет:
  несколько правил на поле, активность на уровне группы, а ключ активной
  уникальности обрастёт `owner` → `(owner, vendor_id, field_path)`.

## Дизайн: Auth

- Users + roles + доступы.
- Роль admin → эксклюзивные операции (напр. vendor delete).
- Пользовательская активация правил/групп: связка `user ↔ rule`
  (напр. таблица `user_rule_state`); «активные для валидации» считаются
  в разрезе конкретного юзера.
- Юзер может удалять только созданные им правила.

## Технические нюансы — окружение и фреймворк (грабли, на которые уже наступали)

- **Spring Boot 4 / Spring MVC 7:** маршруты матчатся БЕЗ трейлинг-слеша.
  `/api/vendors/` ≠ `/api/vendors` → падает в 500 (NoResourceFoundException).
  URL-ы писать точные, без слеша на конце.
- **Jackson XML — это `tools.jackson.*` (Jackson 3.x), НЕ `com.fasterxml.jackson.*`.**
  Импорт `tools.jackson.dataformat.xml.XmlMapper`.
- **`ddl-auto: validate`:** Hibernate таблицы НЕ создаёт (только `schema.sql`
  вручную) и НЕ проверяет строго nullability. `@Column(nullable=false)` в entity
  держать синхронно с `NOT NULL` в БД руками.
- **PostgreSQL `TIMESTAMPTZ` в нативном запросе приходит как `java.time.Instant`,
  не `OffsetDateTime`.** Конвертить: `((Instant) row).atOffset(ZoneOffset.UTC)`.
- **Порядок flush у Hibernate:** на коммите сначала все INSERT, потом UPDATE, потом
  DELETE. Если констрейнт/частичный уникальный индекс требует «сначала обновить,
  потом вставить» — форсить `repository.flush()` между операциями (кейс:
  деактивация старого правила перед вставкой нового).
- **Lombok + boolean:** поле называть `active` (не `isActive`) → геттер `isActive()`,
  без ломбоковской двойной `is`.
- **Spring Security ещё не подключён** (закомментирован в pom) — включаем в Auth.

## Доменные решения и конвенции (наши, чтобы не переоткрывать)

- **`invoiceId` = `sellerTaxId + "|" + invoiceNumber`** — композитный ключ фактуры;
  используется в ValidationService, ValidationBatchDao, таблице `batch_invoice`.
- **`CanonicalFieldRegistry` — единственный источник правды по `field_path`**
  (пути + экстракторы). Новое поле = регистрируем там; `isSupported()` для проверки
  на входе.
- **Операторы:**
    - разделитель `BETWEEN` = `;` (константа `BETWEEN_DELIMITER`), `IN`/`NOT_IN` = `,`;
    - строковые операторы (`EQUALS`, `NOT_EQUALS`, `IN`, `NOT_IN`, `CONTAINS`) —
      регистронезависимы (`equalsIgnoreCase` / `toLowerCase(Locale.ROOT)`);
    - `OperatorEvaluator` НИКОГДА не бросает — безопасный парсинг через `Optional`;
      нечисло для числового оператора → `false` (правило нарушено).
- **Двухэтапная валидация:** бизнес запускается ТОЛЬКО если техническая прошла
  (нужен `CanonicalInvoice`).
- **Severity бизнес-issue = WARNING**, никогда ERROR — бизнес не должен ронять фактуру.
- **Дубликаты:** in-batch (Set) + cross-batch (DAO), оба WARNING; cross-batch НЕ
  делает `continue` (фактура валидируется дальше).
- **Счётчики `ValidationOutput`:** от distinct-фактур; дубликаты — отдельная
  информационная ось; инвариант `validInvoices + invoicesWithIssues = totalInvoices`;
  дубликат-issue исключаются из «с проблемами».
- **`ValidationIssue.message`** — одна чистая фраза, БЕЗ `\n`, БЕЗ префикса severity
  и БЕЗ дублирования полей, которые уже есть отдельно (severity/taxId/ruleKey/
  fieldPath). Форматирование — забота фронта.
- **Известный пробел:** `ValidationIssueEntity` НЕ хранит `message` → при чтении
  отчёта из БД message = null (есть только в ответе на `/validate`). Решить, надо ли
  персистить.
- **API-ответы:** коллекции → `ListResponse<T>` с record-DTO; НЕ отдавать сырые `Map`
  с динамическими ключами. POST/PUT возвращают ресурс; DELETE → 204.
- **Уникальность правил проверяем в коде** (ruleKey, поле) + констрейнты БД как
  страховка (defense in depth) → чистый 409 до похода в БД.
- **`@NotBlank` строже, чем `NOT NULL`** (режет null/пусто/пробелы, 400 на входе).
  Три слоя: `@NotBlank` (модель) + `@Column(nullable=false)` (entity) + `NOT NULL` (БД).
- **Формат передаётся явно** через `@RequestParam("format")`; авто-определение по
  байтам отвергнуто как ненадёжное.
- **`handleUnexpected` обязан логировать** исключение (`log.error("...", ex)`) —
  иначе 500-е немые.
- **`KsefInvoiceMapper` — чистый копировщик**, доверяет техвалидатору (тот бежит
  первым и гарантирует обязательные поля); сам не валидирует.
